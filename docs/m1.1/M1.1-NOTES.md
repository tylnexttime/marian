## 2. Patch 0001: exactness floor (design C-24, C-10)

**The hole (M1.0, section 2.4):** at `--moe-cache-mib 4000` the IQ1_M group (layers 8, 13, 37) got 180 slots. A slot-map
step selects up to `n_tokens x n_expert_used` experts per layer, so the 19, 21 and 28-token prompt chunks (190-280
selections) failed `get_slot_map`'s capacity check; below the op offload batch size (32) their host experts ran on the
CPU. Three CPU-computed prompt steps, three changed answers.

**The fix** (`src/llama-moe-cache.cpp`, constructor): every group first gets

```
n_floor = min( min(n_ubatch, max_batch) * n_expert_used , n_expert )      max_batch = 32 (get_slot_map)
```

slots: the distinct experts of one layer that the largest ubatch on the slot-map path can select (the per-step check
is per layer, so the cap is `n_expert`, not `n_expert x layers`). Then the budget is split as upstream does (by host
bytes, so each group caches the same fraction of its experts), except that a group whose share is below its floor is
held at the floor and the other groups split the rest by bytes (iterated until stable). **When no floor binds, the split
is exactly upstream's.** If one device's budget cannot cover the sum of its floors, the constructor throws
`MoE cache: X MiB on CUDA0 is below the exact-mode floor of Y MiB ...; use --moe-cache-mib Z or more, or a smaller
--ubatch-size`, instead of upstream's silent "not cached" (which also computes on the CPU). A ubatch above 32 tokens takes
upstream's selective copy, which is a GPU path as long as op offload is on (the CUDA offload threshold is 32, so every
ubatch size has a GPU path); `--no-op-offload` now logs a warning that this breaks C-10.

**Logging:** per group at INFO (`-lv 4` to see it): slots, %, MiB, floor, "(held at the floor)". A group held at its floor
is also a WARN, visible in a default server log: `llama_moe_cache: 3 layers of iq1_m experts held at the exact-mode floor
of 320 slots (ubatches up to 32 tokens), their share by size was smaller`.

**Swift 1.5 IQ2_XS, n_ubatch 512** (arithmetic from the GGUF strides and the CUDA 128-byte alignment, same code path):
floor 320 slots per group; the three floors take 1,222.6 MiB, so budgets below **1,223 MiB are refused**; the floor binds
below about **7,050 MiB**.

| Budget MiB | upstream slots IQ2_S / IQ2_XXS / IQ1_M | M1.1 slots |
|---|---|---|
| 2,400 (M1.0 floor arm) | 1,234 / 398 / 108 | 1,105 / 356 / **320** |
| 4,000 | 2,058 / 665 / 180 | 1,973 / 637 / **320** |
| 6,500 | 3,345 / 1,081 / 294 | 3,329 / 1,076 / **320** |
| 9,400 | 4,838 / 1,564 / 426 | 4,838 / 1,564 / 426 (unchanged) |

Consequence: M1.1 hit rates at 2,400-6,500 MiB are not directly comparable with M1.0's (the two big groups lose 1-10%
of their slots); at 9,400 the configuration is identical.

## 3. Patch 0002: fill trace with expert ids (P0b)

The P0 trace has counts and bytes per step, not expert ids. With `MARIAN_MOE_TRACE_FILLS=<file>` each slot-map lookup
also writes one line per uploaded expert: `F,t_us,layer,n_ids,expert,slot,src,bytes`. `t_us` and `layer` equal the
lookup's S line in `MARIAN_MOE_TRACE`, so the two join exactly. `src`: `m` host tensor (upstream), `t` tier hit, `a` read
and admitted into the tier, `r` read through the ring. Separate file, so the P0 CSV and `analyse_m10.py` are unchanged.
`run_arm_m11.ps1` turns it on (`<tag>.fills.csv`).

## 4. Patch 0003: P3 minimal (opt-in, default = upstream)

```
--moe-miss-source mmap|ring|tier     default mmap: the host tensor, i.e. today's path, untouched
--moe-tier-mib N                     pinned RAM tier (tier only)
--moe-ring-mib N                     pinned staging ring, default 64
MARIAN_MOE_SOURCE_VERIFY             unset: load-time check; all: check every read; 0: no check
```

`src/llama-moe-source.{h,cpp}` (new), wired into `copy()` of the cache (only the upload loop; the slot map, the plan and
the SLRU are unchanged). **The large-batch selective copy (`sched_copy_experts`, ubatches above 32 tokens) still uploads
from the memory map: P3 minimal covers slot-map misses (decode and short prompt chunks), not prefill speed.**

- **Reads:** Windows `CreateFileW(FILE_FLAG_NO_BUFFERING | FILE_FLAG_OVERLAPPED)`, up to 16 reads in flight (one per
  expert tensor); Linux `O_DIRECT` + `pread`. The sector size is queried (`FILE_STORAGE_INFO`, max of logical and
  physical-for-performance), offsets rounded down and lengths up to it, buffers aligned to it; the expert is cut out of
  the aligned read (`region = round_up(nb2, sector) + sector` per tensor). A failed unbuffered open falls back to buffered
  reads with a WARN; a failed read uploads that tensor from the host tensor (same bytes) and is counted.
- **File offsets:** the model now keeps the path of each memory-mapped file (`llama_model::weight_file_range`); a host
  tensor's file offset is its address minus the map's base (Windows and POSIX map whole files at offset 0).
- **Ring:** `--moe-ring-mib / slot` slots of one expert (all its tensors); reused only after a synchronize (the copy
  callback's own one at the next layer, or an explicit one when a step wraps the ring).
- **Tier:** pinned slots per cache group, split by host bytes like the VRAM budget, in chunks of at most 1 GiB (pinning
  failures fall back to pageable memory and are reported as PAGEABLE in the load line).
- **Tier policy:** decayed counts (halved every 256 decode steps of a layer) of the distinct experts selected in decode
  steps (`ids <= 8 x n_expert_used`, upstream's "ubatch <= 8" bucket). A decode miss not in the tier is read into a free
  tier slot, else into a CLOCK victim's slot only if its count is higher than the victim's (TinyLFU-style admission;
  reference bits set by decode hits), else through the ring.
- **Prefill guard:** steps above 8 tokens never count, admit or set reference bits; they only read the tier. The tier is
  pinned, so a prefill streaming the GGUF through the page cache cannot evict it either. Slots read or uploaded from in
  the current step are never victims (generation stamps).
- **Load line (WARN, visible by default):** `llama_moe_source: Marian P3 (experimental) tier: ring 43 x 1.46 MiB, tier
  slots per group: ..., N MiB pinned, sector 4096, unbuffered reads, verified against the memory map`. If the source
  cannot be used it says why and the cache keeps upstream's uploads.
- **No exceptions:** this build has no `/EHsc` (the M1.0 build script's `CMAKE_CXX_FLAGS` override drops it), so a throw
  would not unwind; the source reports errors through `error()` and frees its pinned memory itself.

### Why the output stays bit-identical, and how it is proved

Only the host pointer of each upload changes: the same `ggml_backend_tensor_set_async(bank, src, slot*nb2, nb2)` per
expert tensor as upstream, so the same bytes land in the same slots and the same `MUL_MAT_ID` kernels read them. The
proofs, from cheapest to strongest:

1. **Load-time check (automatic):** before the tier is pinned, the first and last expert of every cached tensor are read
   through the source and compared with the memory map; a mismatch drops the source.
2. **CPU self-test (done, no GPU):** `p3_selftest.exe` drives the source with the ggml CPU backend as the device over both
   Swift shards and compares every filled bank slot with the memory map. Three configurations (tier 16 / 64 / 256 MiB,
   ring 64 / 8 / 1 MiB, one with `VERIFY=all`): **42,069 expert tensors, 0 mismatched**, through 1,754 tier hits, 351
   admissions, 11,918 ring reads and 2,242 ring wraps, 0 failed reads.
3. **`VERIFY=all` arm on the GPU (to do):** every read compared with the memory map before its upload; a mismatch aborts
   the server, so a failed request is the signal.
4. **Output identity on the GPU (to do, the real test):** greedy text and top-3 probabilities of the ring and tier arms
   against the mmap arm of the same build at the same budget, 10/10, with the fill trace showing non-zero `t`, `a` and `r`
   counts (so the test could have failed). Checks 1-3 cannot see a slot overwritten while its DMA is still in flight;
   only 4 can, and repeated rounds make a race visible.

## 5. The trace-replay probe (`tools/replay_probe.cu`)

Replays the S-line fill sequence of a P0 trace against three miss sources and reports host time per decode token
(sum over its 48 layer steps of the time from the first upload to the stream sync) and GB/s:

- `mmap`: `cudaMemcpyAsync` from the mapped GGUF (pageable; consecutive experts coalesced, slightly optimistic);
- `ring`: unbuffered overlapped reads (sector query, `--qd` reads in flight) into a pinned ring, upload on completion;
- `tier`: a pinned tier of `--tier-mib` filled at start by unbuffered reads (fill rate reported); fills outside it go to
  the ring.

Expert offsets come from the GGUF headers of both shards (tensor directory + data offset; stride from the gap to the next
tensor), cross-checked against every S line's bytes (a mismatch aborts: wrong model for the trace). **Ids:** the P0 trace
has no expert ids, so without `--fills` they are SYNTHETIC (per layer a seeded permutation ranked by Zipf `--zipf` 1.2; the
`--cache-mib` share of top ranks taken as VRAM-resident, misses drawn from the rest by popularity; tier = oracle ranking
by expected misses per byte). The physical rates are real; the tier hit rate under synthetic ids is a model output. With
`--fills` (a run with patch 0002) the ids are real, the tier is ranked on the first `--train-frac` of steps and the
statistics are taken on the rest. The summary ends with a linear what-if: ms per token for a tier share of 0-100% of the
miss bytes, from the measured ring and tier per-byte times.

`--leave-gib G` holds private memory until only G GiB are available, after pinning the ring and the tier, to reproduce
the server's memory pressure (M1.0: 0.06-0.18 GiB free); without it the mmap pass sees a warmer page cache than the
server did. `--dry-run` parses everything and stops before any CUDA call.

Dry run on `r2-c9400` (done, CPU only): 48 MoE layers, 33.02 GiB of routed experts, layouts 34 x 1,510,400 B / 11 x
1,305,600 B / 3 x 1,177,600 B per expert, every S line consistent with the GGUF; phases decode + post: 2,396 decode
tokens and 23 prompt steps, **61.6 MiB uploaded per decode token (median; p10 20.2, p90 132.0)**; a 6,144 MiB tier holds
4,587 experts. A full run moves about 160 GiB per source; at M1.0's effective 0.95 GB/s the mmap pass alone takes about
3 minutes.

## 9. Risks and doubts

1. **No GPU run yet.** The async hazard (a ring or tier slot rewritten while its DMA is in flight) is argued from the
   synchronize points and generation stamps, and only the GPU output-identity test can catch a mistake there.
2. P3 minimal does not touch prefill: ubatches above 32 tokens still fault through the memory map, and a 6 GiB pinned
   tier leaves less page cache for them.
3. The tier starts empty (no routing profile yet) and TinyLFU admission is conservative once it is full; the self-test
   admitted far fewer experts than it read. Whether the hit share is enough is what arm C and the fill trace measure.
4. Pinning 6 GiB on Windows may fail or be slow; the load line reports PAGEABLE memory if it falls back.
5. The floor changes the M1.0 configurations at 2,400-6,500 MiB (section 2), and refuses budgets below 1,223 MiB that
   upstream would run (with CPU fallbacks).
6. The probe's synthetic ids make its tier hit rate a model output; its mmap pass depends on the page-cache state
   (`--leave-gib`), and it coalesces mmap uploads more than the server does.
7. `GGML_OP_OFFLOAD_MIN_BATCH` above 33 would reopen a CPU gap for 33..N-token ubatches; not checked in code.
8. The build has no `/EHsc` (inherited from the M1.0 build flags; kept for comparability with the measured binaries).
