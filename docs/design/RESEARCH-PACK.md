### Same GGUF: Strata against the older stock build

The most useful same-files comparison is Strata v0.2.2 against stock llama.cpp `3cf03257`. Strata’s quick benchmark reported **35.5 tok/s median chat decode**, range **16.5–53.7**, over nine observations; **155 tok/s at 4K** and **193 tok/s at 16K** prompt length. Its first-token figures were **0.96 s** for chat, **26 s** at 4K and **83 s** at 16K. The stock `llama-bench` runs found **7–10.6 tok/s warm decode** at `tg128`, and **5–6 tok/s cold** as the measurement author’s summary. At `-ngl 99 -ncmoe 32 -fa 1`, measured `pp512` results in the useful runs were about **66–71 tok/s**. Separate `pp4096` results were **113.81 ± 1.95** and **130.39 ± 8.02 tok/s**, with the latter using `-ncmoe 34 -ub 512`. Stock 16K prefill was not measured. These synthetic, depth-zero `llama-bench` decode runs are not the same workload as Strata’s chat and protocol requests. Strata placed **6,836 of 24,576 layer-expert pairs** in its frequency-ranked GPU cache, using **9.16 GiB** for those experts. Its reported decode lookup hit rate was **75,318 / 88,222 = 85.4%**. Stock `-ncmoe 32` instead placed all **8,192** experts of layers **32–47** on the GPU, using **11.36 GiB** for those layers. Its **33.3%** GPU share is arithmetic, not a measured cache hit rate: 16 of 48 complete layers are GPU-resident, irrespective of routing. Stock’s other 32 layers’ routed experts remain on the CPU. ## 2. Upstream llama.cpp at the pin: storage and execution

### Whole tensors at load time; selected experts at execution time

The attached `qwen4exp` loader creates one three-dimensional routed down-expert tensor per layer with shape **`[n_ff_exp, n_embd, n_expert]`**, and creates gate/up expert tensors through `create_tensor_gate_up_exps`. Its router, shared-expert and non-expert weights are separate tensors. The generic MoE graph also accepts a combined `gate_up_exps` tensor where an architecture supplies one. These are tensor-level model allocations: `-ot` chooses a buffer type for a named tensor, not separate buffer types for individual slices of its third dimension. [llama.cpp/src/models/qwen4exp.cpp:217-220](llama.cpp/src/models/qwen4exp.cpp) [llama.cpp/src/models/qwen4exp.cpp:275-282](llama.cpp/src/models/qwen4exp.cpp) [llama.cpp/src/llama-graph.cpp:2141-2162](llama.cpp/src/llama-graph.cpp) [llama.cpp/common/arg.cpp:2757-2779](llama.cpp/common/arg.cpp)

For an expert tensor, upstream’s cache and selective copier use **`w->nb[2]` as the byte stride of one expert** and offset expert `e` by **`e * w->nb[2]`**. Cache layout grouping checks tensor type, shape and this stride. That supplies a concrete route from an expert ID to bytes within an otherwise whole-layer GGUF tensor; it does **not** mean ordinary `-ot` can place individual experts independently when loading the model. [llama.cpp/src/llama-moe-cache.cpp:167-176](llama.cpp/src/llama-moe-cache.cpp) [llama.cpp/src/llama-moe-cache.cpp:591-605](llama.cpp/src/llama-moe-cache.cpp) [llama.cpp/src/llama-context.cpp:2802-2804](llama.cpp/src/llama-context.cpp) [BASELINE.md:154-159](BASELINE.md)

`-ot`/`--override-tensor` accepts tensor-name patterns and buffer types. `--cpu-moe` appends an override keeping MoE weights on the CPU; `--n-cpu-moe N` applies MoE-expert overrides to the **first N layers**. The latter is exactly the placement lever used in the older stock baseline. The pinned arguments additionally expose `--moe-cache-mib N`, default **0**, to reserve a GPU cache for otherwise CPU-kept experts. [llama.cpp/common/arg.cpp:2757-2789](llama.cpp/common/arg.cpp) [BASELINE.md:110-121](BASELINE.md)

`build_moe_ffn` computes router logits, selects top experts with `ggml_argsort_top_k`, gathers and optionally normalises their router weights, then uses `MUL_MAT_ID` for their projections. Its ordinary call supplies the selected expert IDs. If a cache slot lookup is available, `build_lora_mm_id` instead supplies cached bank weights and **slot IDs** to `ggml_mul_mat_id`. The graph subsequently weights and adds expert outputs; cache placement does not change which IDs the router selected. [llama.cpp/src/llama-graph.cpp:2220-2258](llama.cpp/src/llama-graph.cpp) [llama.cpp/src/llama-graph.cpp:2304-2356](llama.cpp/src/llama-graph.cpp) [llama.cpp/src/llama-graph.cpp:1706-1717](llama.cpp/src/llama-graph.cpp) [llama.cpp/src/llama-graph.cpp:2516-2579](llama.cpp/src/llama-graph.cpp)

The scheduler assigns graph nodes to backends and splits the graph when an input cannot be consumed from its existing backend buffer, creating a copy on the consuming backend. It registers a weight-copy callback; for host-buffer input weights that callback can replace copying the *entire* tensor. The callback is invoked after the split’s non-weight inputs have been copied. Thus there are two distinct upstream behaviours when a layer’s weights are host-resident: a backend may compute where those weights live, or a GPU split can receive selected expert bytes instead of a whole-tensor upload. It is not generally correct to say every host-resident expert matmul always executes on the CPU. [llama.cpp/ggml/include/ggml-backend.h:320-327](llama.cpp/ggml/include/ggml-backend.h) [llama.cpp/ggml/src/ggml-backend.cpp:1512-1545](llama.cpp/ggml/src/ggml-backend.cpp) [llama.cpp/src/llama-context.cpp:2778-2859](llama.cpp/src/llama-context.cpp)

The **selective expert copy** callback is particularly relevant. `llama_context::sched_new` registers `sched_copy_experts`. On a split whose first node is `MUL_MAT_ID` using the copied weight, it reads that node’s IDs back, calls `ggml_backend_synchronize`, marks unique selected experts and uploads consecutive ranges. For large batches with a cache it first copies resident expert ranges device-to-device, then uploads the remainder from host memory; a small padding copy protects CUDA MMQ’s last expert. Its ID state resets before each graph compute. The supplied log identifies the refactor as commit `6753a033`, PR **#29943**, and the implementation is present in the attached pin code. [llama.cpp/src/llama-context.cpp:723-729](llama.cpp/src/llama-context.cpp) [llama.cpp/src/llama-context.cpp:2766-2769](llama.cpp/src/llama-context.cpp) [llama.cpp/src/llama-context.cpp:2788-2859](llama.cpp/src/llama-context.cpp)

The loader’s automatic lazy-read threshold is **larger than 4 GiB** for eligible tensors when lazy mode is not explicitly forced on; if mmap is unavailable, it warns and loads the tensor in full instead. `qwen4exp` marks the PLE embedding tensor `TENSOR_READ_LAZY`. Its graph gathers PLE rows and its input path calls `llama_prefetch_rows` where prefetch is available. This is why the **26.82 GiB table** should not be counted as wholly resident host RAM in the baseline. The attached stock run used mmap and lazy mode `auto`. ## 3. Upstream’s own `--moe-cache-mib` cache

This is **already a per-expert device cache**, although its admission and miss handling differ substantially from Strata’s. It is off unless `--moe-cache-mib` supplies a positive budget. The attached log identifies its introduction as **#29887**, multi-GPU extension as **#30112**, and replacement of its LRU policy with a **50/50 SLRU** as **#30637**. The attached `llama-moe-cache.cpp` implements the resulting SLRU and multi-device grouping. [llama.cpp/common/arg.cpp:2780-2789](llama.cpp/common/arg.cpp) [llama.cpp/src/llama-moe-cache.cpp:15-29](llama.cpp/src/llama-moe-cache.cpp) [llama.cpp/src/llama-moe-cache.cpp:187-241](llama.cpp/src/llama-moe-cache.cpp)

**Eligibility.** The constructor collects a layer’s non-null `ffn_gate_up_exps`, `ffn_gate_exps`, `ffn_up_exps` and `ffn_down_exps`. It caches that layer only if **every** collected expert tensor is a **host-buffer weight** and a GPU backend exists for the layer’s assigned device. A partially host-resident set is passed over. It rejects tensor-parallel split mode; context initialisation also disables scheduler pipeline parallelism when an MoE-cache budget is set. With no eligible layers the cache logs a warning and is disabled. [llama.cpp/src/llama-moe-cache.cpp:156-183](llama.cpp/src/llama-moe-cache.cpp) [llama.cpp/src/llama-moe-cache.cpp:255-301](llama.cpp/src/llama-moe-cache.cpp) [llama.cpp/src/llama-context.cpp:525-563](llama.cpp/src/llama-context.cpp)

**Storage.** A device owns a budget and buffer. Its eligible layers are partitioned into groups sharing that device and the same expert-tensor layout. Each group has an SLRU across its layers, one bank per expert tensor role, and one **host I32 slot map per layer**, initially filled with `-1`. Bank tensors are shaped like their reference expert tensors except that their third dimension is **`n_slots + 1`**. The extra slot is not cache capacity: the code states that CUDA MMQ can read past the last expert. The usable bank views have `n_slots` in that dimension. A binding maps each original host expert tensor to its cached GPU view. [llama.cpp/src/llama-moe-cache.cpp:201-250](llama.cpp/src/llama-moe-cache.cpp) [llama.cpp/src/llama-moe-cache.cpp:304-312](llama.cpp/src/llama-moe-cache.cpp) [llama.cpp/src/llama-moe-cache.cpp:388-470](llama.cpp/src/llama-moe-cache.cpp)

The SLRU’s host data includes each layer’s expert-to-slot map, a slot-to-`layer*n_expert+expert` key table, probation and protected linked lists, and generation-stamped IDs for de-duplicating the present request. All slots start in probation. A hit moves a slot to the protected tail; if more than half the slots become protected, the protected head is demoted to probation. A missing expert takes an empty slot or evicts from probation first, then protected, while avoiding every expert selected in the current layer request. It sorts missing IDs before assigning victims so consecutive expert and slot ranges can sometimes be uploaded together. These are recency/repeat-use rules, **not a persistent routing-frequency ranking**. [llama.cpp/src/llama-moe-cache.cpp:15-50](llama.cpp/src/llama-moe-cache.cpp) [llama.cpp/src/llama-moe-cache.cpp:52-153](llama.cpp/src/llama-moe-cache.cpp)

**Budget.** The requested byte budget is apportioned among devices with eligible host experts according to `--tensor-split`, or, by default, their reported free memory. If those shares sum to zero, eligible devices receive equal shares. Within each device, each layout group gets a share proportional to the total bytes of that group’s host expert tensors, with the stated aim that groups cache the same fraction of their experts. Slot counts are increased only while the aligned `n_slots + 1` bank allocation fits that group’s share. A group with fewer slots than the maximum `n_expert_used` is not cached. If no group can hold one token’s expert set, construction throws **“MoE cache is too small to hold the experts of one token”**. An allocation failure also throws. [llama.cpp/src/llama-moe-cache.cpp:304-365](llama.cpp/src/llama-moe-cache.cpp) [llama.cpp/src/llama-moe-cache.cpp:436-453](llama.cpp/src/llama-moe-cache.cpp)

**Small-step execution.** The graph builds routing weights early, obtains the selected expert IDs and, if eligible, inserts a `GET_ROWS` of the host slot map. This host-weight lookup creates a scheduler split; the graph assigns the lookup to the cache’s GPU backend. At the copy callback, upstream finds that lookup and its selection input, reads the selected IDs to host with `ggml_backend_tensor_get_async`, then calls **`ggml_backend_synchronize(backend)`**. It plans SLRU hits and fills; if the selected set exceeds the slot count it aborts. For each expert tensor role, it uploads missing expert bytes into the group’s bank, merging consecutive IDs that also received consecutive slots. It then uploads the updated I32 slot map. The bank’s `MUL_MAT_ID` subsequently indexes **slot IDs**, while the separate routing weights still refer to the model-selected experts. [llama.cpp/src/llama-graph.cpp:2352-2357](llama.cpp/src/llama-graph.cpp) [llama.cpp/src/llama-graph.cpp:2582-2621](llama.cpp/src/llama-graph.cpp) [llama.cpp/src/llama-moe-cache.cpp:549-616](llama.cpp/src/llama-moe-cache.cpp) [llama.cpp/src/llama-graph.cpp:1706-1717](llama.cpp/src/llama-graph.cpp)

**Batch boundary.** `max_batch` is **32 tokens**. The cache’s slot-map path is unavailable for zero tokens, more than 32 tokens, or when the conservative bound `min(n_tokens*n_expert_used, n_expert)` exceeds the group’s slot count. Larger batches do **not** fill and churn the SLRU. Instead, the normal selective-weight-copy path may use `copy_experts` to copy already-cached expert ranges from GPU banks into the batch’s GPU weight copy; uncached selections are uploaded from host. The cache remains available for subsequent decode. This is neither a general 32-token maximum for llama.cpp nor an assertion that every batch of 32 fits a small cache. [llama.cpp/src/llama-moe-cache.cpp:230-236](llama.cpp/src/llama-moe-cache.cpp) [llama.cpp/src/llama-moe-cache.cpp:496-547](llama.cpp/src/llama-moe-cache.cpp) [llama.cpp/src/llama-context.cpp:2833-2854](llama.cpp/src/llama-context.cpp)

**Reporting and omissions.** Startup logs each eligible device’s cache MiB versus host-expert MiB, and each group’s layer count, slot count and capacity percentage. Destruction logs cumulative **hits, misses, hit rate and uploaded MiB** separately for ubatches of at most eight tokens and larger small-cache ubatches; it separately logs large-batch experts copied from cache and their MiB. The attached source does not provide a per-token hit-rate record or a frequency histogram. [llama.cpp/src/llama-moe-cache.cpp:472-485](llama.cpp/src/llama-moe-cache.cpp) [llama.cpp/src/llama-moe-cache.cpp:608-633](llama.cpp/src/llama-moe-cache.cpp)

**Absent from this implementation:** a profile-based warm fill, persistent routing statistics, frequency-ranked admission, a dedicated pinned-RAM expert tier, an explicit NVMe tier, CPU computation *alongside the bank matmul* for cache misses, next-layer prediction, predictive prefetch, pinned staging for the cache uploads, or overlapping those missing-expert uploads with that layer’s cache-bank computation. In its small-cache path, a miss is uploaded and then consumed from the GPU bank. These are statements about the attached implementation, not claims that no other upstream subsystem has any prefetch or speculation feature. [llama.cpp/src/llama-moe-cache.cpp:15-153](llama.cpp/src/llama-moe-cache.cpp) [llama.cpp/src/llama-moe-cache.cpp:549-616](llama.cpp/src/llama-moe-cache.cpp) [llama.cpp/src/llama-model-loader.cpp:1088-1119](llama.cpp/src/llama-model-loader.cpp) [llama.cpp/common/speculative.cpp:73-85](llama.cpp/common/speculative.cpp)

## 5. Strata’s design and numerical boundaries

### Residency, source tiers and miss work

Strata’s GPU `ExpertCache` is slot storage plus a `(layer, expert) → slot or -1` residency table, not the whole execution system. It supports uniform blobs and native-pack slots sized for each assigned expert, laid out consecutively at **256-byte-aligned** offsets. It checks actual free device memory before allocation. An old unprofiled, first-arrival, global admission policy filled slots disproportionately in early layers; per-layer admission gave each layer a fixed range but still did not evict. The profile and adaptive tier are the mechanisms that move beyond those initial policies. [strata/src/core/expert_cache.hpp:19-22](strata/src/core/expert_cache.hpp) [strata/src/core/expert_cache.hpp:84-111](strata/src/core/expert_cache.hpp) [strata/src/core/expert_cache.hpp:152-183](strata/src/core/expert_cache.hpp) [strata/src/core/expert_cache.cpp:563-595](strata/src/core/expert_cache.cpp)

Its `STRP` profile reader accepts a version-1 header, model geometry and ranked `(layer, expert)` pairs. The source describes those pairs as ranked by routing frequency. It refuses a geometry mismatch. A learned-profile writer orders resident experts first, then descending measured heat, with the old profile as a tie-break, and writes via a temporary file and rename. Thus Strata has both an offline warm-start ranking and a path to persist a learned ranking for another start. [strata/src/core/expert_cache.hpp:40-73](strata/src/core/expert_cache.hpp) [strata/src/core/expert_cache.cpp:74-140](strata/src/core/expert_cache.cpp) [strata/src/core/expert_cache.cpp:143-211](strata/src/core/expert_cache.cpp)

During a verify window the dispatcher counts routed usage per pair, groups entries selecting the same expert, sends GPU-resident experts to device groups, and gives a configured share of distinct misses to a GPU PCIe lane **when their source is pinned**. Other misses become CPU-pool jobs. It publishes the GPU plan and queues GPU fetches before running those CPU jobs; the resulting routed rows retain their original output positions for later weighted combination. The pool’s native kernels cover quantised native expert layouts, while the file source or RAM arena supplies their exact bytes. [strata/src/core/expert_source.hpp:364-390](strata/src/core/expert_source.hpp) [strata/src/core/expert_source.hpp:628-644](strata/src/core/expert_source.hpp) [strata/src/core/expert_source.cpp:4779-4828](strata/src/core/expert_source.cpp) [strata/src/core/expert_source.cpp:4829-4961](strata/src/core/expert_source.cpp) [strata/src/core/expert_source.cpp:5024-5180](strata/src/core/expert_source.cpp)

Strata describes an all-experts-in-pinned-RAM normal mode, with CPU computation of uncached experts concurrent with GPU work, and a low-RAM mode that keeps a compact CPU-side complement of GPU residents. Its source also allows a **budgeted** RAM complement chosen in profile rank order, with remaining experts backed by mapped model files. On Windows it checks both available physical RAM and available commit before taking that budget. It has file-backed expert loading from `experts.bin` or native GGUF role slices and can select unbuffered reads when memory pressure makes file-cache retention unsuitable. These distinctions matter on the reference 32 GB machine: saying “every expert is pinned in RAM” would misdescribe a budgeted or fallback run. [strata/docs/HOW_IT_WORKS.md:20-31](strata/docs/HOW_IT_WORKS.md) [strata/src/core/expert_source.hpp:724-749](strata/src/core/expert_source.hpp) [strata/src/core/expert_source.cpp:3493-3564](strata/src/core/expert_source.cpp) [strata/src/core/expert_source.cpp:861-931](strata/src/core/expert_source.cpp)

Strata’s CPU workers normally use one logical processor per physical core, reserve a core for the host thread, and use OS topology rather than assuming SMT siblings. Its source says the pool may compute distinct missed experts once across multiple tokens in a verification window, splitting rows across workers. This is a materially different miss path from upstream’s small-batch cache, which uploads each missing expert before using its bank. [strata/docs/DETAILS.md:2082-2107](strata/docs/DETAILS.md) [strata/src/core/expert_source.hpp:663-674](strata/src/core/expert_source.hpp) [strata/src/core/expert_source.cpp:5056-5180](strata/src/core/expert_source.cpp) [llama.cpp/src/llama-moe-cache.cpp:582-614](llama.cpp/src/llama-moe-cache.cpp)

With `--pcie-frac`, Strata sends the specified fraction of missed experts across PCIe for GPU computation; the CPU pool gets the rest. Its CUDA single-GPU automatic rule, when eligible and not explicitly overridden, refines the share using measured CPU-pool time and a probed link rate, up to three changes in the first decode windows. The documented formula is **`L / (L + 1.85 R)`**, rounded in **0.05** steps and bounded **0.10–0.60**, where `R` is expert bytes divided by CPU time and `L` is measured PCIe speed. Its own documentation says changing that CPU/GPU split can change the final bits because the lanes round differently. [strata/docs/DETAILS.md:1913-1941](strata/docs/DETAILS.md)

The reference Strata run had `STRATA_ROUTE_TAIL_SKIP=7` on. It skipped **6,661** low-ranked missed expert selections. The rule skips a missed expert only when *every* token in the verification window ranked it at position seven or lower; an expert already in GPU cache is still served, and other router weights are **not renormalised**. This is an explicitly **answer-changing** default, not part of an exact comparison against stock. `STRATA_ROUTE_TAIL_SKIP=0` turns it off. Strata reports small measured KL and high top-1 agreement in its own tests, but neither means identical output. ### Prompts, prediction and optional transfers

Strata’s normal prompt path processes chunks of up to **8,192 tokens** with experts streamed over PCIe; its ring and chunk choice depend on pack blob sizes and available room. It retains conversation state and prompt-cache prefixes for follow-up requests. A Linux file-tier host planner can choose a smaller chunk to reduce repeat file reads, but the documentation says **Windows unbuffered file-tier reads keep the existing chunk choice**. It also says changed chunk geometry can change floating-point results even without changing weights. A separate short-prompt CPU share, on by default for eligible single-CUDA-GPU chunks under **1,024 tokens**, times CPU and GPU work and can change last-bit outputs; memory-short configurations may skip its default activation. [strata/docs/HOW_IT_WORKS.md:48-53](strata/docs/HOW_IT_WORKS.md) [strata/docs/DETAILS.md:1813-1836](strata/docs/DETAILS.md) [strata/docs/DETAILS.md:1943-1970](strata/docs/DETAILS.md) [strata/docs/DETAILS.md:2298-2315](strata/docs/DETAILS.md)

Strata supports MTP drafting and prompt-lookup drafting, with the large model checking proposed tokens. Its documentation says the MTP helper drafts up to three, and prompt lookup can draft up to five when earlier context is useful. The attached reference run used a separately fetched **5.2 GB** MTP draft layer and recorded **93 accepted of 130** drafts in an initial request. Verification preserves the target model’s decision in Strata’s description; **Inference:** that claim does not turn the whole measured Strata configuration into an exact stock baseline, because route-tail skip and CPU/GPU rounding remain in effect. [strata/docs/HOW_IT_WORKS.md:35-46](strata/docs/HOW_IT_WORKS.md) [strata/docs/DETAILS.md:2297-2301](strata/docs/DETAILS.md) [strata-build/RESULTS.md:21-23](strata-build/RESULTS.md) [strata-build/RESULTS.md:57-64](strata-build/RESULTS.md)

For file-tier look-ahead, Strata copies a later layer’s BF16 router to the host, applies it to the current layer’s activation on a worker, drops already-resident predictions and warms predicted expert pages. The source is explicit that this prediction **only warms bytes** and does not change which experts are eventually selected or computed. There are optional Linux I/O workers, page-residency probes, confidence/deadline/byte-budget admission and feedback from whether read-ahead was used. A different, optional `STRATA_FS_SLOTS` mechanism reserves VRAM swap slots, fetching missed or predicted experts ahead; Strata’s documented whole-engine screens found no consistent gain after the smaller main cache was accounted for, so it remained off. `STRATA_DMA_BATCH=1` is an experimental CUDA-13-or-newer way to submit independent pinned-host uploads with `cudaMemcpyBatchAsync`; mode `2` adds an overlap hint where supported. Both keep the same copied bytes. A 16 × 2 MiB transfer microbenchmark reduced median host submission from **0.0936 to 0.0162 ms**, but median total transfer from only **2.5589 to 2.5248 ms**. ## 8. Marian M0: existing reusable work

M0 is a **pre-release Python 3.10+**, standard-library tool with `machine`, `inspect`, `profile`, `plan` and `serve` commands. Its llama.cpp adapter binds a real `llama-server` to **127.0.0.1**. Its `Config` already has a `moe_cache_mib` field and the adapter emits upstream’s `--moe-cache-mib` when that field is set. That is CLI support, not M0 measurement or control of per-expert residency. [marian/README.md:1-9](marian/README.md) [marian/marian/cli.py:23-36](marian/marian/cli.py) [marian/marian/engines.py:20-60](marian/marian/engines.py)

`machine.py` reads GPU identity, VRAM, driver and PCIe fields through `nvidia-smi`, and total/available RAM through Windows `GlobalMemoryStatusEx` or Linux `/proc/meminfo`. Its 12-hex-character fingerprint hashes CPU identity, RAM rounded down to GiB and GPU name/VRAM/driver; hostname is separately hashed for the reported machine record rather than included in that fingerprint key. **Inference:** Driver changes can change the fingerprint and separate otherwise comparable profile files. [marian/marian/machine.py:17-44](marian/marian/machine.py) [marian/marian/machine.py:47-96](marian/marian/machine.py)

`gguf.py` reads GGUF **header metadata only**, not tensor payloads. It returns architecture, file type, block count, trained context, expert count, selected-expert count, hidden width and whether the model is MoE. Its reported `bytes` is the size of the supplied path. **Not found in the material:** M0 inspection of all split shards’ expert tensor types, per-expert strides or the reference PLE table. [marian/marian/gguf.py:1-5](marian/marian/gguf.py) [marian/marian/gguf.py:45-76](marian/marian/gguf.py)

For each requested context and KV type, `profile.py` walks MoE `-ncmoe` positions from CPU-heavy towards GPU-heavy, starts a server, fills roughly **75%** of context with fixed neutral text, requests a fixed number of generated tokens, and records server prompt/decode speed and sampled peak VRAM/lowest available RAM. It labels a point `overflow` when observed VRAM is within its default **300 MiB** margin or decode speed is below **0.6** times the best preceding point, then stops that walk. The default sampler interval is **0.5 s**. Its JSON contains `marian_profile: 1`, UTC measurement time, machine and engine records, model ID/metadata, probe settings and rows. Model identity is the first **64 MiB plus file size** hashed to 12 hex characters, not a whole-shard content hash. `plan.py` loads files matching the current fingerprint and model ID, admits only `status: ok` rows with sufficient measured context, then chooses the **smallest qualifying context** and the fastest measured row *within that context* for prompt or decode objective. It refuses to extrapolate to an unmeasured context. Its `to_config` reconstructs context, KV, thread and whole-layer split, but does **not** restore the optional `moe_cache_mib` field.
