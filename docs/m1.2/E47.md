# E47: how predictable is Swift's expert routing, at which horizon, and what is perfect prediction worth?

Register E47, pre-registered 27/10/2026 07:05, before any number was computed; run the same day. Offline and CPU only:
`marian predict` (`marian/predict.py`, tested first on SYNTHETIC traces with known answers in `tests/test_predict.py`)
read the M1.2 routing-id traces of Swift 1.5 IQ2_XS at `-ncmoe 48 --moe-cache-mib 9400` (48 MoE layers, 10 of 512
experts per token). The question behind it: before building an early router or a learned probe, bound what predicting
the routing could buy, on traces we already have.

```
python -m marian predict <runs-dir>/i2-c9400.ids.bin --geometry <runs-dir>/swift-local.geometry.json --budget-mib 9400 \
    --requests <runs-dir>/i2-c9400.requests.jsonl --trace <runs-dir>/i2-c9400.trace.csv \
    --check-against <runs-dir>/i1-c9400.ids.bin --permutations 100 --seed 47 --md <out>/predict-i2.md --json <out>/E47.json
```

About 45 s on the laptop's CPU. The same inputs and seed give the same report byte for byte (two runs compared).

## What counts as what

- **Decode token:** the single-token S steps of one forward pass of a request, all 48 layers present (the selection
  `replay` and `analyse_m10.py` use). The test set is decode prompts 1, 3, 5, 7, 9 (1,209 tokens; 1,204 with a
  previous token); training is prompts 0, 2, 4, 6, 8 (938 tokens; prompt 2 stops after one token).
- **Prefill:** L records, multi-token S records, and the 1-row step at layer 47 that closes every prompt pass.
  llama.cpp computes the last layer for the logits row only, so that step has `n_tokens == 1` but is no token.
- **Never read:** the server's warm-up (96 steps outside every request), the `warm` request (prompt 0's first tokens
  again), anything between requests.
- **post-pp16K class:** `post:0` and `post:1`. Their routing is identical, token for token, to `decode:0`'s and
  `decode:1`'s first 127 tokens; `post:2` has no decode token.

## Pre-registered rules and verdicts

- **Persistence:** +17.59 points over the null, so not within 5. **Token-horizon id prefetch stays a candidate.**
- **Itinerary:** co-occurrence at h = 1 is 19.23%, against 38.32% for the better baseline (persistence): -19.09 points.
  It does beat the null (p = 0.0099), but the rule needs both. **Layer-ahead prediction from ids is dead.** The
  hidden-state route needs its own case before any patch.
- **Prefill-to-decode:** +0.02 points (pp4k) and +6.63 (pp16k), under 10 in both. **Not promoted.**
- **Oracle:** perfect prediction one layer ahead from pinned memory gives 20.49 tok/s, +41.3% over the measured 14.5
  tok/s of the tier (E44). That is not under 10%, so the rule's "prefetch is not the decode lever" does not follow.
  **The register names no decision for this branch.**

## Implementation choices (declared in `marian/predict.py`)

- **Ties at the k-th place:** split fractionally (the expected score under a random tie-break).
- **Persistence:** a token counts at w only with w predecessors.
- **Itinerary predictor:** sums the co-occurrence count rows of layer l's experts.
- **Itinerary null:** a random cyclic permutation (never the token itself), with one partner per token for all its
  layers. p = (1 + nulls at or above real) / 101.
- **N per layer:** the group's slots divided by its layers, which is 142 for all three groups at 9,400 MiB.
- **Prefill sets:** an expert the prefill never used is never in a set.
- **Oracle, T:** the interval between consecutive decode tokens' layer-0 lines. It reproduces the server's `gen_tps`
  per request (4.09 against 4.09 for prompt 1).
- **Oracle, units:** GB/s = 1e9 bytes/s, as the copy probe prints them.
- **Oracle, tok/s:** the all-tokens rate, as E44's 14.5 is. A request's last token is left out (no interval).

## Read with care

- **The oracle's token-horizon row.** Taken as written, every layer's copy may hide behind the whole previous token
  (window C per layer). For mmap at 0.41 GB/s that gives 20.50 tok/s, although a token's 60 MiB of misses take about
  150 ms at that rate. With one serial copy engine (not pre-registered) it is 5.46. No verdict uses that cell.
- **The request horizon.** The register gives no window for it. It is read as "the source becomes pinned, nothing
  hidden" (17.85 tok/s).
- **C = T - H is not a pure compute time.** It correlates with host time (r = 0.54) and with miss bytes (r = 0.40).
  The oracle inherits it as the spec defines it.
- **Short requests.** The pp requests have 31 decode tokens each, not 32. The first generated token comes from the
  prefill pass.
- **Layer 47 in the prefill.** The prefill routes layer 47 for its output row only. Without layer 47 the
  prefill-to-decode difference is +1.26 points (pp4k) and +7.89 (pp16k), still under 10.
- **The post-pp16K class.** `post:0` is a training prompt, so its itinerary and prior figures are in-sample (37.80%
  and 13.74%).
